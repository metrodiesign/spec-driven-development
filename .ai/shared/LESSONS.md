# Lessons (promoted from retrospectives)

- **Pattern**: pure-logic-first — แยก logic ที่ทดสอบได้ (สูตร/validation) เป็น pure function ใน `lib/` แล้ว unit test เขียวก่อนแตะ UI. — **Why**: ความถูกต้องไม่ปนกับ rendering, ปิด acceptance ที่เป็นตัวเลขก่อน wire UI.
- **Pattern**: /spec-analyze ก่อน design คุ้มเสมอสำหรับฟีเจอร์ที่มี logic — จับ conflict/gap ที่ทำให้ test เขียนไม่ได้ (หน่วย/วิธีปัดเศษ, trigger คำนวณ, empty state, conflict รูป-ต้องมีเน็ต-vs-ห้าม broken). — **Why**: แก้ที่ requirements ถูกกว่าแก้โค้ดทีหลัง.
- **Pattern**: audit vuln แยก **dev-only chain vs prod-core** ก่อนตัดสิน (`npm ls <pkg>` ชี้เจ้าของ) -> dev chain (vitest→vite→esbuild, แม้ "critical" UI-server) ไม่ bundle prod = bump dev major แก้ได้สะอาด (vitest v2→v4 API `defineConfig`/`test.include`/`resolve.alias` เสถียร — หมายเหตุ: bump v4 ทำใน scaffold session 06-02 ที่ไม่ถูก commit; branch ปัจจุบัน vitest ^2.1.8 สถานะ vuln chain ต้อง audit ใหม่); core-transitive (postcss ที่ next bundle, `next→postcss`) flag + ระบุเงื่อนไข resolve, ห้าม `npm audit fix --force`. — **Why**: fix --force downgrade core dep เป็น breaking (next->9.x) เลวกว่าตัว vuln; เหมารวมทุก vuln เป็น "ต้อง fix" จะ downgrade core ทั้งที่ตัวจริงเป็น devDep แก้ได้ด้วย bump major. ต้องรอ upstream bump เฉพาะ core.
- **Pattern**: รัน long-running server (`next start`) โปรเจกต์นี้ผ่าน `rtk proxy npx next start` เพื่อเห็น raw log ("Ready"/error). — **Why**: rtk hook rewrite output เป็น summary ("Errors: 1 | Warnings: 0") บดบัง log จริง -> เข้าใจผิดว่า server พังทั้งที่ขึ้น 200.
- **Pattern**: cost จริงอ่านจาก ledger `.cost.total_cost_usd` เท่านั้น ห้าม recompute จาก transcript (overcount 1.6-3.7x) — รายละเอียด dedup/การปันส่วน/ข้อจำกัด ledger: `.claude/skills/spec-retro/references/cost-accounting.md`. — **Why**: ระบบคำนวณ cost ให้แล้วผ่าน statusline; recompute เองได้เลขผิดเสมอ.
- **Pattern**: headless `claude -p` buffer output จนงานจบ — pane ว่าง/CPU ต่ำ ≠ ค้าง. ก่อนฆ่า ตรวจ progress บน disk (`git status`, ไฟล์ใหม่, node_modules) ไม่ใช่ดู pane. และ `--permission-mode acceptEdits` ครอบแค่ Edit ไม่ครอบ Bash -> npm/scaffold ติด permission เงียบใน headless (ต้อง `--dangerously-skip-permissions` หรือ `--allowedTools`). — **Why**: เคยฆ่า scaffold ที่กำลังทำงานเพราะ pane ว่าง.
- **Pattern**: หลัง command fail อ่าน output ให้จบก่อนยิงใหม่; แก้ script แล้ว **Read กลับยืนยันการแก้ (โดยเฉพาะ `cd`/path)** ก่อนรัน. error เดิมซ้ำ 2 ครั้ง = หยุด. — **Why**: ลืม `cd` ใน resume-pane ซ้ำ 4 รอบเพราะ re-fire background blind ไม่อ่านผลรอบก่อน + ประกาศ "แก้แล้ว" โดยไม่ได้แก้บรรทัดจริง.
- **Pattern**: `tasks.md` checkbox ขัดกับ git log (commit อ้าง task เสร็จ แต่ checkbox ยัง `[ ]`) เชื่อ **filesystem** เป็น ground truth ก่อนเริ่ม — `ls app/` / `find package.json` ดูว่ามี artifact จริงไหม. retrospective-only commit (docs ไม่มีโค้ดคู่) ทำให้ branch ดูคืบหน้าทั้งที่ว่าง. — **Why**: เกือบข้าม task 1 (scaffold) เพราะ log มี commit "task 2-9" แต่ `app/` ไม่มีจริง; เชื่อ log = report ผิด/skip บนฐานที่ไม่มี.
- **Pattern**: `git diff --stat` / `--name-only` **ไม่เห็นไฟล์ใน path ที่ยัง untracked** (โปรเจกต์นี้ `app/` ทั้งโฟลเดอร์เป็น `??`) -> retro/handoff ที่ gather "Files Modified" จาก git stat อย่างเดียวจะ **ตกหล่นโค้ดจริง** (เห็นแต่ spec/docs ที่ tracked). เช็ก `git status` (เห็น `??`) ควบคู่ + จำจาก session เอง. — **Why**: รายงานว่า "ไม่มีโค้ดเปลี่ยน" ทั้งที่แก้ component จริง เพราะ stat เงียบเรื่อง untracked.
- **Pattern**: "assemble page" task เป็นจุดจับ gap ของ requirement ระดับ section — ก่อนประกอบ cross-check **ทุก section ใน REQ-1.1 (list ลำดับหน้า) เทียบ component ที่มีจริง + anchor ใน nav data**. เคสจริง: Articles (REQ-13) ไม่ถูก task 4 (static) หรือ 5 (interactive) list เลย แต่ REQ-1.1 ต้องมี + `MAIN_NAV` มี `#articles` -> assembly เป็นที่เดียวที่จับได้. component ที่ขาด = สร้างเป็น prerequisite ของ assembly (blocker ของ REQ-1.1 ไม่ใช่ scope creep) แล้ว **flag ดัง + บันทึก gap-fill ใน tasks.md** ไม่แก้เงียบ. — **Why**: decomposition ที่แบ่ง task ตาม verify-modality (static tsc vs interactive browser) ทำ section ตกร่อง (Articles เป็น static แต่ไม่อยู่ task 4 list); ไม่ cross-check ลำดับหน้า = ส่งหน้าขาด section ทั้งที่ทุก task ย่อยผ่านในขอบเขตตัวเอง.
- **Discovery**: multi-session แพงกว่า all-in-one ~30-40% สำหรับ coupled feature — แยก session เพื่อ accuracy เท่านั้น (conscious trade ไม่ใช่ cost win); kernel การตัดสินใจอยู่ที่ `.claude/commands/pane-loop.md` + spec-tasks/SKILL.md, ตัวเลข/วิธีคิด cost ของ multi run: `.claude/skills/spec-retro/references/cost-accounting.md`. — **Why**: เคยเชื่อกลับด้าน (แยก=ถูกกว่า) → default ผิด.
- **Pattern**: PreToolUse hook block (exit 2) ฆ่า compound command **ทั้งก้อน** — setup ที่มัดมาในก้อนเดียวกัน (chmod, mkdir, cp) ไม่รันเงียบๆ. แยก setup ออกจากคำสั่งที่เสี่ยงโดน block, หลังโดน block ให้ไล่เช็กว่าส่วนไหนของก้อนยังไม่ได้รัน, และก่อน commit ตรวจ mode ใน index (`git ls-files -s`) ของ script ทุกตัว. เคสจริง: `hook-bypass-guard.sh` เข้า commit เป็น 100644 เพราะ `chmod +x` อยู่ก้อนเดียวกับ test ที่ destructive-guard block — เจอตอน `git log --stat` แก้ด้วย amend ก่อน push. หมายเหตุประกอบ: hook ที่เพิ่ม/แก้ใน settings.json มีผล**ทันทีกลาง session** (ไม่ใช่ snapshot ตอนเริ่ม) — เหยื่อรายแรกของ guard ใหม่อาจเป็นคำสั่งทดสอบของตัวเอง; test harness ที่มี destructive string ใน argument ให้เขียนเป็นไฟล์ /tmp แล้วรัน ไม่ใช่ inline. — **Why**: เชื่อว่า chmod รันแล้วเพราะอยู่ในคำสั่งที่ "ส่งไปแล้ว" ทั้งที่ hook ตัดก่อน execute → ไฟล์ mode ผิดหลุดเข้า commit.
- **Pattern**: guard/regex hook เขียนเสร็จห้ามเชื่อจนกว่าผ่าน adversarial test เป็นไฟล์ test suite (bypass case + false-positive case ด้วยเคสจริง รันผ่าน stdin JSON) — regex ที่ผ่านตา+ผ่าน test ชุดที่ผู้เขียนนึกออก ยังโดน fresh-context reviewer เจาะได้ 8 ทาง (indented rm, /bin/rm, xargs, git clean แยก flag, combined short flag -nm, hooksPath override) และ false positive ข้ามคำสั่ง (grep -r ตามด้วย rm -f โดน AND ของ flag คนละคำสั่ง). — **Why**: ผู้เขียน test เฉพาะเคสที่ตัวเองนึกออก; reviewer ที่ถูกสั่งให้ "craft bypass แล้วรันจริง" จับ failure mode ที่ผู้เขียนมองไม่เห็นเสมอ.
- **Pattern**: ผล Workflow/subagent review เชื่อไม่ได้ถ้ามี `<failures>` — verifier ที่ตายกลางทาง (spend-limit / terminal error) คืน verdict null, partition แบบ `f.verdict?.isReal` ตีเป็น falsy แล้วตกเข้า `rejected` เงียบๆ ปนกับ finding ที่ถูก refute จริง. ก่อนเชื่อ rejected/confirmed: นับ `<failures>` เทียบจำนวน verifier ที่ควรรัน; verifier ไหนตาย ให้ re-verify finding นั้นด้วยมือกับไฟล์จริง อย่าถือ rejected = ไม่ใช่ปัญหา. ออกแบบ harness ให้ verdict ที่หายไป = "ยังไม่ตัดสิน" (ไม่ใช่ rejected) จะปลอดภัยกว่า. — **Why**: เคส Tier 4 review verifier 16/17 ตาย แต่ผลส่ง `confirmed:1, rejected:16` ดูเหมือนผ่านเกือบหมด ทั้งที่ rejected ส่วนใหญ่ไม่เคยถูกตรวจ — ถ้าเชื่อตามจะ ship 7 bug จริง.

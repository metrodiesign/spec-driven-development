## Lessons Learned

- **Pattern**: ก่อน ship validation ที่เข้มขึ้น (strict schema / reject-unknown) ต้อง grep archived specs หา guarantee เก่าฝั่งตรงข้าม (เคสจริง: Phase-1 REQ-8.4 "preserve-and-ignore unknown keys" + test `some_future_key` ยัง live) — ถ้าชน ให้ประกาศ supersession เป็น criterion + changelog แทนการปล่อยพฤติกรรมกลับด้านเงียบ; เช่นเดียวกับ guarantee ของ stage ก่อนใน pipeline เดียวกัน (Stage-1 REQ-4.5 "resolved draft freezes unchanged" ตายทันทีที่ freeze เริ่ม reject `risk: "TODO"`) — **Why**: fresh-context auditor จับได้เพราะไล่ archive; ถ้าหลุดไป test เก่าจะแดงแบบงง ๆ หรือแย่กว่า — ถูกแก้ให้ผ่านโดยไม่มีใครบันทึกว่า guarantee หาย — **Classification**: advisory
- **Pattern**: fail-closed guard ต้อง mirror เงื่อนไขของ action ที่มันป้องกันครบทุก flag (เคสจริง: guard เช็คแค่ `planning.enabled` แต่ dispatch จริงต้องการ `enabled && plannerRoleTrigger` → refuse config ชอบธรรมที่ไม่มี dispatch เกิด — Codex P2) พร้อม regression test ฝั่ง negative (เงื่อนไขไม่ครบ + สภาพที่ guard จะ trip → ต้องรันผ่าน) — **Why**: fail-closed ที่กว้างเกินเงื่อนไขจริงกลายเป็น availability regression บนเส้นทางปกติ; requirement แบบ WHILE-<action> แปลว่า guard ยิงเฉพาะ path ที่ action เกิดจริง — **Classification**: advisory
- **Pattern**: wiring test (config → consumer) ต้องใช้ค่า non-default เสมอ — default ชนกัน (contract template 3 == `RepairPolicy` default 3) ทำให้ test ผ่านแม้สายไม่เคยต่อ — **Why**: spec-architect จับตอน design (AD‑แนว D7); ใช้ค่า 5 แล้ว assert พฤติกรรม (PROBE_RUN = 5) คือหลักฐานเดียวที่แยก "ต่อสายแล้ว" ออกจาก "บังเอิญเท่ากัน" — **Classification**: advisory

## Lessons Learned

- **Discovery**: Bash tool ไม่มี real TTY (`process.stdin.isTTY` = `undefined`) แต่ live-command guard สไตล์ `decideLiveRun` ต้องการ `isTTY===true` — ขับคำสั่ง live ผ่าน iTerm2 pane จริง (`osascript`'s `write text`, เทคนิคเดียวกับ `pane-loop.sh`), redirect output ไปไฟล์ log + ต่อ sentinel (`; echo DONE_EXIT_$? >> log`) ให้ `run_in_background` wait จบแม่นยำ (grep ข้อความ error เดิมเปราะ เพราะแต่ละ failure path คนละคำ). — **Why**: เป็นวิธีเดียวที่ผ่าน TTY guard โดยไม่ต้องแก้ guard เอง, reusable กับ live/manual task ใดๆ ในอนาคต.
- **Discovery**: OpenAI Structured Outputs "strict mode" (`codex exec --output-schema` ตรวจด้วย) ต้องการ `additionalProperties:false` ทุก object node + `required` ครบทุก property (optional = nullable type ไม่ใช่ absent) + `items` ชัดเจนทุก array แบบ recursive — Anthropic ไม่ต้องการทั้งหมดนี้เลย. — **Why**: ไม่มีบันทึกไว้ในโปรเจกต์นี้มาก่อน (SPIKE-6 ไม่เจอ); ต่อ adapter ให้ vendor ตระกูล OpenAI ตัวไหนก็ตามในอนาคตต้องผ่าน strict-mode schema นี้ด่านแรกเสมอ.
- **Pattern**: `check-core-vendor-free.sh` (INV-7) scan `core/`+`aal/` หา vendor name **รวม comment** ทั้งต้นไม้ (ตั้งใจ) — ตั้งชื่อ vendor ตรงๆ ใน comment ของ Ring 0/1 พังทั้งที่ logic ไม่เปลี่ยนเลย ต้องใช้คำกลาง ("strict-schema lineage", "cross-lineage") แม้ใน prose. — **Why**: commit แรกของ session นี้ผ่าน test/typecheck ทุกอย่างแต่ CI แดงเพราะ comment เอ่ยชื่อ vendor.
- **Pattern**: task ที่ mark `[x]` ด้วย CI เขียวอาจพิสูจน์แค่ "แต่ละชิ้นแยกกันทำงานถูก" ไม่ใช่ "ทั้ง pipeline ต่อกันจริง" — ก่อนพึ่ง end-to-end flow (เช่น approve → continue → merge) ที่ข้าม task หลายตัว ให้ grep หา caller จริงของฟังก์ชัน connective (เช่น `buildApprovalPackage`) ก่อนสมมติว่ามันถูกเรียกจาก production path. เคสจริง: F-Loop approve (task 8) + auto-merge (task 5) แต่ละตัว CI เขียวด้วย hand-fed test fixture, แต่ไม่มี production code ต่อ REVIEWING → human-approval → merge เข้าด้วยกันเลย. — **Why**: เกือบเสีย live quota พยายาม approve งานผ่าน F-Loop จริงก่อนเจอว่า pipeline นั้นไม่เคยต่อสาย.
- **Discovery**: post-merge automated review (Codex บน GitHub PR) เจอบั๊กจริง 4 จุด **หลัง** ที่ manual live-verification + 568 test เขียวหมดแล้ว — 2 จุดเป็นโค้ดที่เพิ่งเขียนใน session เดียวกันนี้เอง (แก้ครึ่งเดียว: message ดึง detail ที่ถูกแล้วแต่ classification ยังลืมใช้ detail เดียวกัน). — **Why**: live/manual verification เก่งเรื่อง "ทำงานได้จริงตาม happy path ที่ทดสอบ" แต่ไม่ได้แทนที่ static code review สำหรับ edge case ที่ไม่ได้ exercise สด (custom port, typo'd flag, unused ref) — เปิด PR ไว้ให้ automated review วิ่งแม้หลัง merge แล้วคุ้มเสมอ, อย่าข้ามเพราะ "ทดสอบสดผ่านหมดแล้ว".

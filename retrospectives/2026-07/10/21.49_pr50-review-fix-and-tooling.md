## Lessons Learned

- **Pattern**: ตรวจ comment ของ automated PR review (Codex ฯลฯ) กับ **spec/requirements ก่อนแก้ตาม** เสมอ — ไม่ใช่แค่กับโค้ด. เคสจริง: Codex บอกว่า fix ก่อนหน้า (route fusion panel ผ่าน `baseRouter` เพื่อกัน stats pollution) ผิด เพราะ REQ-16.2/AZ-13 บังคับ planner ต้อง dispatch ผ่าน router ตัวเดียวกับ task loop — ถ้าเชื่อ Codex ตรงตัวจะ revert เป็นของเดิมที่ผิด spec คำตอบจริงคือกลไกที่สาม (`record:false` peek) ไม่ใช่สองตัวเลือกที่มีอยู่. — **Why**: bot review บอกกลไกถูกแต่บางทีวิธีแก้ที่มันแนะ (หรือที่เรา fix ไปก่อน) ขัด spec ที่มันไม่รู้จัก ต้อง cross-check เอง.
- **Discovery**: teammate ที่ตายกลาง task เพราะ transient API error (เช่น Cloudflare 522, `retryable:true` ใน error body) ไม่เสียงานที่ทำไปแล้ว — `SendMessage` ไปชื่อเดิมหลังรอ `retry_after` จะ resume จาก transcript เดิมพร้อม context ครบ สั่งให้เช็ค `git status`/branch ก่อนทำต่อเพื่อไม่ทำงานซ้ำ. — **Why**: เกือบ spawn teammate ใหม่ทั้งที่ของเดิม (branch + progress) ยังอยู่ครบ — resume ถูกกว่า restart เสมอเมื่อ error เป็นฝั่ง infra ไม่ใช่ฝั่งงาน.
- **Pattern**: skill ที่ผลิตไฟล์ output (เช่น session-report) ให้ระบุ path ไป scratchpad ตรงๆ ไม่ปล่อยตาม default `cp` ที่อิง cwd — cwd ระหว่าง session อาจเป็น repo root ทำให้ report/scratch file หลุดเข้า working tree ของ repo โดยไม่ตั้งใจ (ต้องมาเก็บกวาดตอน retro/commit). — **Why**: เคสจริง session นี้: `session-report-*.html` ไปสร้างที่ root ของ spec-driven-development แทน scratchpad.

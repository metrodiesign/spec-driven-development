## 📝 AI Diary

I assumed browser verification would be a quick formality once `tsc` and `build` were green — but it became the bulk of the session. 🤔 I assumed the dropdown "not opening" was my code, and I nearly shipped three different mental fixes before realizing the page wasn't even hydrated. The first real signal I dismissed too long: clicks did nothing, yet I kept re-reading my own JSX.

😕 I was genuinely confused about why a programmatic `.click()` opened the menu but a real Playwright click left it closed, and why `focus()+click()` closed it while `click()` alone opened it. I cycled through "click-outside contains() is wrong", "React batching", "mouseleave fired" — all wrong. The truth had two layers stacked: (1) my `onClick` toggle genuinely fought the hover/focus opener, and (2) the production server I was testing against was a STALE build from before my fix, so I was half-debugging old code.

😮 I expected `localhost:3000` to be my Next dev server because the startup curl said READY, but I got a 401 auth-JSON from an unrelated app squatting IPv4 `:3000`; my Next had quietly fallen back to IPv6. That single DNS-resolution detail (localhost→IPv4) sent me down a long detour. The lesson that finally untangled it: verify `hasReactProps`/fiber presence BEFORE trusting any interaction result, and rebuild after every edit when serving via `next start`.

## What Went Well

- **Pure-event isolation testing**: dispatching `mousedown` alone, `.click()` alone, `focus()+click()` separately → pinned the exact failing combination → proved the component logic was correct once rebuilt (8 dropdown items, ESC restores focus).
- **Honoring lessons.md (action/read split)**: recalling the React async-render lesson stopped me from concluding "UI broken" on the early stale reads → avoided a false bug report.
- **Not killing the foreign :3000 app**: recognized it wasn't mine → sidestepped via IPv6/clean port → no disruption to the user's other running service.

## What Could Improve

- I let the startup `curl -sf` (which silently passes on the wrong server too late) lull me; I should have asserted the response BODY was my HTML, not just a 200.
- I rebuilt the prod server only after wasting cycles on a stale build — the rebuild-after-edit rule should have been reflexive from the first `next start`.
- Spent ~6 turns reasoning about React batching when one `hasReactProps` probe up front would have reframed the whole investigation in one shot.

## Blockers & Resolutions

- **Blocker**: `next dev` pages load but React never hydrates → every interaction is a no-op.
  **Resolution**: Root-caused to a system proxy mangling Turbopack's HMR WebSocket (+ foreign IPv4 :3000). Switched to `npm run build` + `next start` on `127.0.0.1:3006`; confirmed `__reactFiber$` present, then all interactions passed.
- **Blocker**: dropdown opened programmatically but not via real click.
  **Resolution**: Found `onClick` toggle vs hover/focus opener race; changed to open-only. Confirmed after rebuild.

## Lessons Learned

- **Pattern**: When browser interactions are no-ops, probe hydration (`__reactFiber$`/`__reactProps$`) BEFORE blaming component logic — un-hydrated DOM looks like a UI bug. - Why: separates environment failure from code failure in one check.
- **Discovery**: `next start` serves stale `.next`; rebuild after every edit. A startup liveness probe (`curl -sf`, green build) proves _something_ is up, not that it's _your current code_. - Apply: assert response body identity + rebuild, don't trust 200/READY.
- **Pattern**: One-directional dropdown (open on hover/focus/click, close on leave/ESC/outside) avoids the focus-vs-click toggle race while satisfying hover/focus + ESC requirements.

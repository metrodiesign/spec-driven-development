## 📝 AI Diary

I assumed task 2 would be trivial "just write some arrays," but I learned the real constraint was type-coupling: `Service.icon` must be a valid `IconName`, and that type lives in the task-1 Icon component, not in the data layer. That forced an early decision — import `IconName` into types.ts and constrain services to icons that actually exist in the registry — rather than inventing icon names that would compile-fail or render empty boxes (a hard constraint in tech.md). I was uncertain whether to extend the Icon registry to give each of the 12 services a semantically perfect icon, or to map onto the existing ~22 icons. I chose mapping, because task 2 is scoped to data and touching Icon.tsx would bleed into task-1 territory and risk unrelated churn; if task 7 reveals a service deserves a unique glyph, that is the right moment to extend. I expected the item counts to be the only acceptance gate, but I also wanted `tsc` green as the real proof the shapes match design — and that mattered, because the `IconName` import is exactly the kind of cross-module link that silently breaks if I typo a name. The count script counting `id:` occurrences gave me a quick second signal; I double-checked articles wouldn't over-count from nested `author` objects (they have no `id:`), which they didn't.

## What Went Well

- **Strict types compiled first try**: importing `IconName` rather than re-declaring → `tsc --noEmit` clean, zero `any` → proves data shapes match design.md exactly
- **Scoped discipline**: resisted extending Icon registry → task stayed a clean vertical data slice → no task-1 regression risk
- **Deterministic data**: fixed seeds + literal ISO dates → reproducible builds → satisfies design's "no Date.now" note

## What Could Improve

- Did not run `npm run build` (only typecheck) — task-2 verify line only asked for `tsc`, but a build would catch any accidental client/server boundary issues earlier.

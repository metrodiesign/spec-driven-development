ผมงงช่วงหนึ่งตอน verify REQ-19.1: หลัง hover menuitem ครั้งแรกแล้วอ่าน aria-expanded ได้ `false` + menuitemCount 0. ผมเกือบสรุปว่า bridge พัง. จนกระทั่งนึกได้ว่าระหว่าง MCP eval call กับ hover call ที่มี gap เวลานาน pointer/hover state อาจ drift — พอ re-run sequence แบบกระชับ (hover trigger -> hover menuitem -> read ติดกัน) ได้ `true` + clickable. นี่คือ lesson เดิมเรื่อง action กับ read ต้องแยก call แต่บิดมุมใหม่: ไม่ใช่แค่แยก แต่ต้องไม่ปล่อยเวลายาวระหว่าง action ที่อาศัย hover persistence.

## บทเรียนที่ได้ (Lessons Learned)

- **Pattern**: hover bridge = ย้าย gap จาก `mt-1` (margin นอกกล่อง) → `pt-1` บน absolute wrapper ที่ครอบ visible panel; `shadow`/border/bg ต้องอยู่ inner panel ไม่ใช่ wrapper (ไม่งั้น gap เห็น border). verify: elementFromPoint กลาง gap = wrapper โปร่งใส (bg rgba 0,0,0,0) และ li.contains(elAtGap)=true. - กัน dead-zone submenu โดยไม่เพิ่ม dep/timer
- **Discovery**: MCP `browser_evaluate` — `element.focus()` ไม่ persist ข้าม eval call (อ่านรอบถัดไป state หาย) แต่ `page.hover()` persist; เปิด dropdown ที่ต้องวัดข้าม call ให้ใช้ hover. - กันการเสียรอบเดา "ทำไม dropdown ไม่เปิด"
- **Discovery**: overflow ที่ viewport นอก acceptance set (1024) ซ่อนได้แม้ 375/768/1440 เขียว; เมื่อเจอ culprit ของ task อื่น ให้ยืนยันด้วยการวัดตอน feature ของตัวเอง "ปิด/ไม่ทำงาน" (dropdown ปิด -> ยัง overflow = pre-existing) แล้วรายงานไม่แก้. - แยก regression ของตัวเองจาก pre-existing, รักษา task boundary

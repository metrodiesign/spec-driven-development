## Lessons Learned

- **Pattern**: ผล workflow review เชื่อไม่ได้ถ้ามี `<failures>` — verifier ที่ตายกลางทาง (spend-limit/terminal error) คืน verdict null → partition `f.verdict?.isReal` ตีเป็น falsy → ตกเข้า `rejected` เงียบๆ ปนกับ finding ที่ถูก refute จริง. ก่อนเชื่อ rejected list ต้องนับ `<failures>` เทียบจำนวน verifier; ถ้าตาย ให้ re-verify finding นั้นด้วยมือกับไฟล์จริง อย่าถือว่า rejected = ไม่ใช่ปัญหา. — **Why**: รอบนี้ 16/17 verifier ตาย แต่ผลส่ง `confirmed:1, rejected:16` ดูเหมือนผ่านเกือบหมด ทั้งที่ rejected ส่วนใหญ่ไม่เคยถูกตรวจ — ถ้าเชื่อตามนั้นจะ ship 7 bug จริง (Testing-Strategy REQ leak, bugfix Status gate ฯลฯ).
- **Discovery**: default branch ที่ harness รายงาน (gitStatus "usually develop") อาจไม่ตรงกับ integration branch จริง — repo นี้ PR #5/#6 merge เข้า main, develop ตามหลัง 91 ไฟล์. ก่อนตั้ง base ของ stacked PR เช็ก `gh pr view <parent#> --json baseRefName` + `git diff origin/<target> --stat` เลือก base ที่ให้ diff สะอาด (squash-merge ทำ parent commit ไม่ "contained" by SHA แต่ content อยู่แล้ว). — **Why**: base develop จะลาก 91 ไฟล์ homepage ที่ไม่เกี่ยวเข้า PR; เลือก main ได้ diff 13 ไฟล์สะอาด.
